## Import recent history

After deploying an API revision that includes `import-history`, run **Actions → Pilot history import** on `main`, entering that exact deployed commit SHA. The production-gated workflow shares the API deployment lock, checks the running image and database health, and executes `pulse-api import-history` in the existing container. It does not restart services, modify GCP, consume an invite, or require another Supabase sign-in.

The command imports published V3 briefs for the latest 30 UTC dates from the existing public GCS manifest. The report lists expected and missing dates, inserted/unchanged counts, and the number verified against stored JSON and metadata. Missing manifest dates are reported as source gaps; a listed but missing/invalid artifact fails the import. Downloads have per-request and size limits, reject redirects and unexpected artifact URLs, and the whole operation has a three-minute deadline. A changed manifest aborts before writing. Each download uses its exact GCS generation from freshly revalidated object metadata and checks the returned generation. An artifact created at or after the manifest version is rejected as an unfinished publication, even when the manifest content is unchanged. Equal creation timestamps are rejected conservatively; retry after publication completes. This follows GCS [object-version and timestamp semantics](https://docs.cloud.google.com/storage/docs/metadata#timestamps), without changing bucket caching or the publisher.

All inserts and parity checks commit together. Repeating the workflow should report zero inserted rows and all expected dates unchanged. Existing briefs with different payloads or metadata stop the transaction for review; the importer never overwrites a live publication or deletes user data. Inspect the source and stored record before choosing a separate repair. A failed commit acknowledgement is an uncertain outcome: rerun to verify parity before claiming failure or success.

History import bypasses model generation and notification paths entirely, including for today's imported brief. Existing feedback, memberships and notification preferences remain intact. The one-shot workflow remains available alongside the scheduled worker below; both reuse the same atomic importer. Current-day notification recovery and the next real daily-run comparison remain launch requirements before switching pilot app reads.

## Scheduled repair and freshness

After releasing the reconciliation implementation through CI, `RECONCILE_HISTORY_ENABLED=true` in the reviewed public configuration enables an API-owned worker on Hetzner. It runs immediately on startup and every 15 minutes, checking the latest 30 UTC dates without regenerating content. A cycle tries at most three imports, 30 seconds apart; each import has a three-minute deadline and the full cycle an eleven-minute deadline. A separate Postgres advisory transaction lock serializes worker replicas, with a twelve-minute idle timeout to release dead ownership. The worker shares the API's lifetime: restart interrupts the attempt and starts another immediately; replay preserves already committed publications. Manual imports can run concurrently using the importer's own serialization and parity checks.

The persisted singleton checkpoint records start/finish, attempts, last success, consecutive exhausted cycles, a safe error, latest source date and the last complete parity report. `GET /internal/reconciliation` requires the existing pipeline service token; use a private header file or the established secure operator workflow, never a token in chat/logs. A database error or interrupted cycle can leave `outcome=running` with the previous last success intact; no fresh success is invented. Inspect logs/checkpoint and restart/release through CI if necessary. A conflicting live record stops repair for review; there is no automatic overwrite. Repairs send no notifications, even for today, until the P2 outbox is implemented.

`GET /healthz/briefs` is public and returns only `status` and `reason`. It returns 200 only when reconciliation is enabled, the last successful parity check is no more than 45 minutes old (and not more than one minute in the future), and both the source report and active engineering database contain yesterday's brief before 07:30 UTC or today's from 07:30 UTC onward. Otherwise it returns 503. Historical source gaps do not fail this current-feed check. `/healthz` retains its API/database meaning. The probe checks current presence and the most recent completed parity report; it is not a continuous checksum of every row.

**Actions → Pilot feed freshness** runs at minute 23 each hour and supports manual dispatch. It makes bounded public HTTPS requests, rejects redirects/malformed/degraded responses and fails the run when freshness is unconfirmed. No secret or notification sender is added. The failed Actions run is the alert signal; the repository owner must verify Actions failure notifications reach their intended destination before pilot invitations. GitHub schedule delays and notification preferences prevent an exact detection-time guarantee. Verify a real failure notification and recovery, the next scheduled GCP publication, and a controlled API-outage rehearsal after deployment; local tests alone do not close these gates.

To disable repair, change the reviewed public flag to `false` and release the API through CI. Changing a secret's copy of the flag alone has no effect because the public overlay wins. This leaves GCP running and makes the freshness probe degraded by design. Migration `0004_reconciliation.sql` is additive; retain its checkpoint when rolling forward or back to a compatible API. Disabling the worker is not a restoration of missing user data.

## Revoke pilot access / departure

An authorized operator runs this against the Hetzner application database through the existing controlled access process. First identify the exact user UUID and verify the target; do not target a user by display name. Bind `user_id` as a psql variable. This is a procedure, not an automated deployment step.

```sql
BEGIN;
UPDATE users SET is_active = false WHERE id = :'user_id'::uuid;
UPDATE memberships SET notify_email = false, notify_push = false
  WHERE user_id = :'user_id'::uuid;
UPDATE device_tokens SET is_active = false WHERE user_id = :'user_id'::uuid;
UPDATE invites SET expires_at = now() WHERE created_by = :'user_id'::uuid;
COMMIT;
```

Verify the affected row counts. Subsequent authenticated API requests, including signup retries, return 403 even for an unexpired token. In-flight requests may finish. Keep the identity/email record so a fresh invite cannot link around the disabled account; do not delete it as the revocation mechanism. Revoke any shared invite the departing user knows, and ban/revoke their Supabase sessions separately. Revoke recipient/device routing in the legacy notification system through its existing process: this database flag cannot stop GCP legacy delivery or erase an offline client's cached content. Before P2 invitations, the new sender must check `users.is_active` as well as membership/preferences/device ownership.

For account deletion, separately review retention and dependent records, then perform explicit cleanup in both systems. Disabling access is reversible and preserves feedback for that review. Re-enabling a user must not silently re-enable email/push preferences or device tokens.
