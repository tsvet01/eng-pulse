# One sandbox push to one pilot phone

This manual test uses the deployed API executable without enabling the daily sender. It sends **Eng Pulse pilot test** / **Push notifications are working on this device.** Apple accepting the request is not proof of delivery; confirm the alert on the intended phone.

1. Register for notifications in the sandbox build of the pilot app on the physical phone. In GitHub's protected `production` environment set `PILOT_PUSH_TEST_USER_ID` and `PILOT_PUSH_TEST_TOKEN_SHA256` from the **same confirmed registration**. The fingerprint is SHA-256 of the lowercase hexadecimal token **text**, in UTF-8 without a newline. Never paste a device token into GitHub or a workflow input.
2. Keep `NOTIFY_PUSH_ENABLED=false`. The active registered account must be the configured admin with an identity from the configured issuer and push enabled for its active engineering membership. The command checks the exact active iOS sandbox token belonging to that account. No other device is selected if a check fails.
3. The API container can supply its complete existing `APNS_KEY_BASE64`, `APNS_KEY_ID` and `APNS_TEAM_ID`. Otherwise, if all three are empty, set the three names as separate protected environment secrets. They are passed only into the one command. Partial/missing credentials, a non-Apple URL, or a different topic stop the test. No daily configuration or legacy sender is changed.
4. Dispatch **One-device pilot push test** on `main`, using mode `check`, the full SHA of the already deployed API and a fresh UUID for this authorization. The check tests eligibility and local signing-key configuration without reserving the ID or contacting Apple.
5. After approval for this phone, dispatch mode `send` with the **same** SHA and test UUID. At most one POST can be attempted for this authorization, including concurrent runs and workflow reruns. A lost response, crash, timeout or provider refusal spends the ID; never switch IDs to retry. Check the intended phone for the alert. Any future test needs a separate explicit authorization.

For a specific authorization, an operator can inspect `pilot_push_test_attempts` by its `test_id`. An outcome of `accepted` means Apple accepted the request; `reserved` or `not_confirmed` does not establish delivery. The table records no account or device token and never participates in the daily outbox.
